# Service Request Management API

A beginner-friendly REST API for creating and managing service requests. It uses Express and stores requests in a local JSON file, so no database setup is needed for learning.

## Features

- Create, list, view, replace, partially update, and delete service requests.
- Validate required fields, email addresses, and allowed request statuses.
- Save each request in `data/requests.json` with a unique ID and timestamps.
- Return consistent JSON errors for invalid input and missing routes or requests.
- Configure the server port through an environment variable.

## Technologies

Node.js, Express.js, JavaScript, REST, JSON, dotenv, CORS, and Nodemon.

## Project structure

```text
service-request-api/
  controllers/requestController.js  Request logic and JSON-file storage
  data/requests.example.json        Empty starter data copied when the API first runs
  data/requests.json                Local request records (ignored by Git)
  middleware/errorHandler.js        Consistent JSON error responses
  middleware/notFound.js            Handles unknown URLs
  public/                            Frontend files served by Express
    index.html                       Service request portal
    styles.css                       Portal styles
    app.js                           Portal behavior and API calls
  routes/requestRoutes.js           Maps URLs and methods to controller functions
  test-api.js                       Automated API smoke checks
  .env                              Local port setting; do not commit
  .env.example                      Safe environment-variable template
  .gitignore                        Excludes local dependencies and secrets
  package.json                      Dependencies and run commands
  server.js                         Express application entry point
```

The frontend is served from `public/` by the API server.

## Requirements

Install Node.js (an active LTS version is recommended). npm is included with Node.js.

## Installation and run

Open a terminal in `service-request-api` and install the packages:

```bash
npm install
```

In Windows PowerShell, if the `npm` command is blocked by the local script policy, use `npm.cmd` in its place (for example, `npm.cmd install`).

The local `.env` file sets `PORT=3000`. If it is missing, copy `.env.example` to `.env`. Start the server:

```bash
npm run dev
```

Nodemon restarts the server when source files change. For a normal start, use `npm start`. Visit `http://localhost:3000/` to open the portal, or `http://localhost:3000/api/health` to check the API. Stop it with Ctrl+C.

## How routes and controllers work

`server.js` creates the Express app, enables JSON parsing and CORS, serves the portal from `public/`, and mounts the request router at `/api/requests`. `requestRoutes.js` matches each HTTP method and URL to a controller function. `requestController.js` validates input, reads or changes the JSON data file, and sends the response. The not-found middleware and central error handler run after the routes so errors use one consistent format.

## API endpoints

API endpoint responses are JSON. The portal is served at `/`. Request IDs are generated by the API; send the ID from a response when using a `:id` route.

| Method | URL | Purpose | Success |
| --- | --- | --- | --- |
| GET | `/` | Service request portal | 200 |
| GET | `/api/health` | Check server health | 200 |
| GET | `/api/requests` | List every request | 200 |
| GET | `/api/requests/:id` | Get one request | 200 |
| POST | `/api/requests` | Create a request | 201 |
| PUT | `/api/requests/:id` | Replace editable request details | 200 |
| PATCH | `/api/requests/:id` | Update only supplied details, including status | 200 |
| DELETE | `/api/requests/:id` | Delete one request | 200 |

The editable detail fields are `name`, `email`, `service`, and `description`. PUT requires all four; it preserves the current status unless a valid status is included. PATCH accepts one or more of these fields and/or a valid status. IDs and timestamps are generated by the API and cannot be edited. New requests always start as `Pending`.

### Example POST body

```json
{
  "name": "Avery Ndlovu",
  "email": "avery@example.com",
  "service": "Career guidance",
  "description": "I would like help preparing a CV."
}
```

### Example created response (201)

```json
{
  "success": true,
  "message": "Service request created.",
  "data": {
    "id": "generated-uuid",
    "name": "Avery Ndlovu",
    "email": "avery@example.com",
    "service": "Career guidance",
    "description": "I would like help preparing a CV.",
    "status": "Pending",
    "createdAt": "2026-10-16T10:00:00.000Z",
    "updatedAt": "2026-10-16T10:00:00.000Z"
  }
}
```

The ID and timestamp above are examples; the API generates real values.

### Request and response examples

Start the server before sending these requests. For any `:id` URL, replace `PASTE_ID_HERE` with the `id` returned by POST.

**GET `/`** — no body; expect `200` and the service request portal.

**GET `/api/health`** — no body; expect `200`:

```json
{"status":"ok","message":"Service Request API is running."}
```

**GET `/api/requests`** — no body; expect `200` (empty example):

```json
{"success":true,"count":0,"data":[]}
```

**GET `/api/requests/PASTE_ID_HERE`** — no body; expect `200`:

```json
{"success":true,"data":{"id":"generated-uuid","name":"Avery Ndlovu","email":"avery@example.com","service":"Career guidance","description":"I would like help preparing a CV.","status":"Pending","createdAt":"2026-10-16T10:00:00.000Z","updatedAt":"2026-10-16T10:00:00.000Z"}}
```

**POST `/api/requests`** — use the example POST body above; expect `201` and the created-request response shown above.

**PUT `/api/requests/PASTE_ID_HERE`** — send every editable field; expect `200`:

```json
{"name":"Avery Ndlovu","email":"avery@example.com","service":"CV review","description":"Please review my updated CV."}
```

```json
{"success":true,"message":"Service request replaced.","data":{"id":"generated-uuid","name":"Avery Ndlovu","email":"avery@example.com","service":"CV review","description":"Please review my updated CV.","status":"Pending","createdAt":"2026-10-16T10:00:00.000Z","updatedAt":"2026-10-16T10:05:00.000Z"}}
```

**PATCH `/api/requests/PASTE_ID_HERE`** — send only the field to change; expect `200`:

```json
{"status":"In Progress"}
```

```json
{"success":true,"message":"Service request updated.","data":{"id":"generated-uuid","name":"Avery Ndlovu","email":"avery@example.com","service":"CV review","description":"Please review my updated CV.","status":"In Progress","createdAt":"2026-10-16T10:00:00.000Z","updatedAt":"2026-10-16T10:06:00.000Z"}}
```

**DELETE `/api/requests/PASTE_ID_HERE`** — no body; expect `200`:

```json
{"success":true,"message":"Service request deleted.","id":"generated-uuid"}
```

### Errors and status codes

- `200`: Request succeeded.
- `201`: Request was created.
- `400`: Invalid or incomplete JSON input. The response may include an `errors` object naming fields to fix.
- `404`: The requested ID or URL does not exist.
- `500`: Unexpected server or data-file error; internal details are not sent to clients.

For example, an invalid email returns `400` with `{"success":false,"message":"Please correct the submitted fields.","errors":{"email":"Enter a valid email address."}}`.

## Test manually with Postman or Thunder Client

Use `http://localhost:3000` as the base URL. For POST, PUT, and PATCH, choose **Body → JSON** (or set `Content-Type: application/json`). Try the operations in this order so you can reuse the ID from the POST response.

1. `GET http://localhost:3000/api/health` — no body; expect `200` and `{"status":"ok","message":"Service Request API is running."}`.
2. `GET http://localhost:3000/api/requests` — no body; expect `200` and an object with `count` and a `data` array (initially empty).
3. `POST http://localhost:3000/api/requests` — send the example POST body above; expect `201` and the created request, including its generated `id` and `Pending` status.
4. `GET http://localhost:3000/api/requests/PASTE_ID_HERE` — use the returned ID; expect `200` and that request.
5. `PUT http://localhost:3000/api/requests/PASTE_ID_HERE` — send all four editable fields, for example `{"name":"Avery Ndlovu","email":"avery@example.com","service":"CV review","description":"Please review my updated CV."}`; expect `200`, updated details, and a newer `updatedAt`.
6. `PATCH http://localhost:3000/api/requests/PASTE_ID_HERE` — send `{"status":"In Progress"}`; expect `200` and the changed status.
7. `DELETE http://localhost:3000/api/requests/PASTE_ID_HERE` — no body; expect `200` and a deletion message.

Also check failures:

- POST with `{"name":"Avery","email":"not-an-email","service":"Advice","description":"Help"}` returns `400` with an email validation message.
- PUT with a missing required field returns `400`.
- PATCH with `{"status":"Waiting"}` returns `400` because the status is not allowed.
- GET or DELETE `/api/requests/does-not-exist` returns `404`.
- GET `/this-route-does-not-exist` returns `404` with a JSON route-not-found message.
- Send malformed JSON (for example `{`) with `Content-Type: application/json`; expect a `400` JSON error.

For a repeatable automated check, leave the API running in one terminal and run `npm test` from `service-request-api` in a second terminal. The script creates a test request, exercises the API, and deletes the test record. If the API is on a non-default port, set `API_BASE_URL` first, for example in PowerShell: `$env:API_BASE_URL='http://localhost:3001'; npm test`.

## Frontend

The portal in `public/` defaults to the API at `http://localhost:3000/api/requests`, so it can also be opened through a separate local static server such as VS Code Live Server. To point it at an API on another port, add a URL parameter such as `?api=http%3A%2F%2Flocalhost%3A3001%2Fapi%2Frequests`. CORS is enabled for local development; in a deployed application, restrict CORS to your actual frontend origin.

## Data and security notes

The JSON file is useful for learning and small local demonstrations, but it is not a production database. Concurrent writes, backups, access control, and scaling need a database and additional production safeguards. The first API request creates a local `data/requests.json` from `data/requests.example.json` when needed. Runtime request data is ignored by Git so names, email addresses, and descriptions are not accidentally published. Do not store passwords, API keys, or other secrets in source control. `.env` is ignored by Git; `.env.example` contains only a safe sample setting. The API trims text, checks field lengths and email format, and accepts only the allowed status values.
